# 11. Переходы между секциями и смена слайдов

**Зачем:** секция не просто уезжает вверх, а **прогорает**, растворяется или уходит шторкой, и
за ней открывается следующая. А фото в слайдере сменяются не «щелчком», а жидкостью, кругом
или пикселями.

| Эффект | Движок | Файл |
| --- | --- | --- |
| Прожигание, Растворение, Шторка | SVG-фильтр поверх настоящей секции, без WebGL | `src/runtime/transition.js` |
| Смена слайдов | WebGL, две текстуры и прогресс | `src/runtime/runtime.js` + `src/effects/slides.ts` |

## Часть 1. Как прожечь настоящую HTML-секцию

### Почему не «снимок страницы»

Первая мысль: сфотографировать секцию в картинку, отдать её шейдеру и сжечь картинку. Минусы:

- в браузере **нет** стандартного способа сфотографировать HTML (библиотеки вроде
  html2canvas перерисовывают страницу сами и часто ошибаются со шрифтами и картинками);
- пока идёт переход, секция «мёртвая»: видео стоит, текст не выделяется, ссылки не работают;
- прокрутили назад — нужен новый снимок.

Мы делаем иначе: **секция остаётся живой**, а дыры в ней вырезает CSS-фильтр
`filter: url(#k3d-burn-1)`, который ссылается на SVG-фильтр. Браузер применяет его к
секции на каждом кадре, как обычный `blur()`.

### Шаг 1. Поле «когда эта точка прогорит»

Считаем один раз, при запуске: сетка 256 × N клеток (N — по пропорциям секции), для каждой
клетки число — **очередь на прогорание**:

```js
base = расстояние до ближайшего очага      // «Очаги»: дальние горят позже
     | 1 - y                               // «Снизу»
     | расстояние до центра                // «Центр»
     | 0                                   // «Везде» — только шум
value = base + шум × рваность              // фронт огня неровный
```

Шум — тот же fbm, что в шейдерах (глава 02), только на JavaScript, плюс мелкий слой для рваной
кромки.

**Выравнивание по рангу.** Сортируем клетки по `value` и заменяем каждое значение его
местом в очереди: `rank = место / (число клеток − 1)`. После этого:

- значения равномерно распределены от 0 до 1;
- **прогресс 0.3 = прогорело ровно 30 % площади** — при любом узоре и любых очагах.

Без этого «Центр» горел бы медленно в начале (круг маленький) и быстро в конце, а «Везде» —
наоборот.

Поле превращается в серую картинку (`canvas.toDataURL()`) — светлее = горит позже.

### Шаг 2. Фильтр: оставить только «ещё не сгоревшее»

```xml
<filter id="k3d-burn-1">
  <feImage href="data:image/png…"/>                          <!-- поле -->
  <feColorMatrix type="luminanceToAlpha" result="field"/>     <!-- яркость → прозрачность -->
  <feComponentTransfer in="field" result="keep">
    <feFuncA type="linear" slope="250" intercept="-250·t"/>   <!-- порог -->
  </feComponentTransfer>
  <feComposite in="SourceGraphic" in2="keep" operator="in"/>  <!-- секция × маска -->
</filter>
```

`feFuncA linear`: `новая_прозрачность = slope × поле + intercept` (с обрезкой до 0…1). При
`slope = 250` и `intercept = −250·t`:

| поле | 250 × (поле − t) | итог |
| --- | --- | --- |
| меньше t | отрицательное | 0 — дыра |
| t + 0.004 и больше | ≥ 1 | 1 — секция на месте |
| между | 0…1 | мягкий край в пару пикселей |

`SourceGraphic` — это сама секция. `operator="in"` оставляет её только там, где маска непрозрачна.

**Каждый кадр меняется одно число** — `intercept`. Картинка поля не пересчитывается.

### Шаг 3. Тлеющий край — шейдер поверх секции

Первая версия рисовала огонь **тем же SVG-фильтром**: ещё три порога, вычитание масок
(`feComposite arithmetic`), заливки цветом (`feFlood`), размытие для свечения
(`feGaussianBlur`). На обычном экране — 60 кадров. На ретине пользователь увидел 25.

Замер (экран 1728×1117, плотность 2, 120 шагов перехода, трассировка Chrome — сколько кадров
браузер **реально показал**):

| Что в фильтре | Время 120 шагов | Пропущено кадров |
| --- | --- | --- |
| только дыры | 1,0 с | 0 |
| + огненный край | 3,2 с | 263 |
| + копоть | 4,3 с | 410 |
| + свечение (blur) | 7,1 с | 733 |

Каждый шаг фильтра — это промежуточная картинка размером с секцию (на ретине — 3456×2234
пикселей), и браузер пересчитывает всю цепочку на каждом кадре.

> **Почему не видно в обычном замере.** `requestAnimationFrame` показывал ровные 16,7 мс: он
> мерит только JavaScript. Фильтр считается позже, при отрисовке, в другом потоке. Честная
> цифра — сколько кадров дошло до экрана (`DroppedFrame` в трассировке Chrome).

Сейчас фильтр делает **только дыры** (`feImage` → порог → `feComposite in`), а огонь рисует
WebGL-холст поверх секции — один проход шейдера на кадр:

```glsl
float f = texture(uField, uv).r;   // то же поле, что в фильтре
float d = f - uT;                  // < 0 — дыра, чуть больше 0 — горит
float band = smoothstep(-aa, aa, d) * (1.0 - smoothstep(e - aa, e + aa, d));   // огненная полоса
vec3 fire = mix(uHot, uEmber, smoothstep(0.0, e, d));                          // жёлтый → оранжевый
float soot = (1.0 - smoothstep(e, e * 3.5, d)) * …;                            // копоть за огнём
float glow = exp(-(d < 0.0 ? -d * 2.2 : d) / (e * 1.6));                       // свечение, в дыру гаснет быстрее
```

- `fwidth(f)` — насколько поле меняется между соседними пикселями: край сглажен ровно в один
  пиксель при любом размере.
- Огонь лежит на **уцелевшей** стороне (`d` от 0 до `e`) — закрывает край дыры, который режет фильтр.
- Мерцание — шум от времени, у каждого квадратика 3×3 пикселя своё.

Результат на том же замере: **1,0 с, 0 пропущенных кадров**.

**Где лежит холст.** Не поверх всей страницы (`position: fixed`), а в том же контейнере,
сразу после секции, с запасом 80 px вокруг для свечения и пепла. Поэтому окна, шапки и
модалки остаются **над** огнём, а контейнер с `overflow: hidden` обрезает огонь вместе с секцией.
Каждый кадр холст ставится на место секции — у «липкой» секции оно меняется при прокрутке.

**Грабли:** сброс стилей `canvas { max-width: 100% }` (он есть почти на каждом сайте) сжимал
холст огня до ширины контейнера — и огонь съезжал с края дыр. Поэтому у холста
`max-width: none`, а e2e-тест проверяет, что холст шире секции ровно на 160 px.

### Шаг 4. Пепел

Где рождать частицы? Мы **знаем** это точно: клетки поля со значением около `t` — это и есть
горящий край. Клетки уже отсортированы (`order`), поэтому край — это отрезок массива
от `t·N` до `(t + e)·N`. Берём случайные клетки оттуда.

Частицы рисуются тем же WebGL-холстом, точками (не больше 900): поднимаются (тёплый воздух),
покачиваются, меняют цвет жар → пламя → серый пепел и гаснут. Чем быстрее прокрутка, тем
больше пепла: число новых частиц пропорционально изменению прогресса.

### Шаг 5. Запуск

| `trigger` | Как работает |
| --- | --- |
| `scroll` | Прогресс = насколько прокручен «липкий» стек. Назад — секция «зарастает» |
| `appear` | `IntersectionObserver`: показалось ≥ 50 % секции → `play()`; ушла с экрана → сброс |
| `manual` | Только из кода: `play()`, `reverse()`, `progress(0.42)` |

**Липкий стек** — главный приём для перехода при прокрутке:

```html
<div class="stack">
  <section id="leaving" class="stack__top">…первая…</section>
  <section class="stack__under">…вторая…</section>
</div>
```

```css
.stack { position: relative; height: 300vh; }      /* 100vh экрана + 200vh прокрутки на переход */
.stack > * { position: sticky; top: 0; height: 100vh; }
.stack__top { z-index: 2; }                          /* первая — сверху */
.stack__under { z-index: 1; margin-top: -100vh; }   /* вторая — под ней, на том же месте */
```

Обе секции «прилипают» к верху экрана, пока стек прокручивается. Прогресс:

```js
progress = (верх экрана − верх стека) / (высота стека − высота экрана)
```

**С GSAP ScrollTrigger** — `trigger: 'manual'` и прогресс из ScrollTrigger:

```js
const t = mount('#leaving', { trigger: 'manual' })
ScrollTrigger.create({
  trigger: '.reveal', start: 'top top', end: '+=150%', pin: true, scrub: true,
  onUpdate: (self) => t.progress(self.progress),
})
```

### Подводные камни

- **У секции должен быть свой фон.** Иначе «дыра» в прозрачной секции незаметна.
- **Фильтр включается только во время перехода.** При прогрессе 0 — `filter` снят (никакой
  нагрузки), при 1 — `visibility: hidden` (секция не ловит клики поверх следующей).
- **`filter` создаёт новый контекст для `position: fixed`** внутри секции: на время перехода
  «прилипшие» элементы внутри неё прилипают к секции, а не к экрану.
- **«Уменьшить движение»** — вместо огня простое исчезновение (`opacity`).

### Параметры

| Параметр | Что меняет |
| --- | --- |
| Запуск | Прокрутка / появление / из кода |
| Откуда горит | Очаги, везде, снизу, сверху, центр |
| Очагов | Сколько точек загорается первыми |
| Масштаб шума / Рваность края | Форма фронта |
| Ширина края | Толщина огненной полосы (0 — без огня, чистое растворение) |
| Свечение / Копоть / Пепел | Сила эффектов вокруг края |
| Длительность | Для «Появления» и «Из кода» |
| Вариант узора | Зерно случайности: другие очаги и другой шум |
| Жар / Пламя / Копоть | Цвета |

## Часть 2. Смена слайдов шейдером

### Две текстуры и прогресс

Рантайм получает список картинок (`spec.images`) и держит две текстуры: `uFrom` — что было,
`uTo` — что будет, плюс `uProgress` 0 → 1 (уже сглаженный, ease-in-out) и `uDirection`
(1 — вперёд, −1 — назад). Для удобства в шейдер добавлены функции:

```glsl
vec3 fromAt(vec2 uv)   // цвет старого слайда в точке (с object-fit: cover)
vec3 toAt(vec2 uv)     // цвет нового
```

Любой переход — это ответ на вопрос «**сколько нового слайда** в этой точке при таком
прогрессе»:

```glsl
col = mix(fromAt(uv), toAt(uv), m);   // m — 0…1, своя формула у каждого режима
```

| Режим | Формула m |
| --- | --- |
| Жидкость | `smoothstep` порога по шуму: разные места переключаются в разное время; картинки «текут» на `sin(p·π)` — сильнее всего в середине |
| Шторка | Координата вдоль направления (угол) + шум; светящаяся кромка `exp(−|фронт − x| / w)` |
| Круг | Расстояние от курсора (или центра) меньше растущего радиуса; рябь у края сдвигает старый слайд |
| Пиксели | Клетки растут к середине перехода (`mix(200, 12, sin(p·π))`), у каждой клетки свой момент смены |
| Зум | Старый слайд «улетает» с радиальным размытием (8 выборок к центру), новый выезжает из глубины |
| Глитч | Полосы сдвигаются рывками, каналы R и B расходятся, кадр переключается полосами в разные моменты |
| Волна | Круговой фронт от центра или курсора; кольцо `sin((r − фронт)·45)·exp(−|r − фронт|·6)` сдвигает картинку |

Важная мелочь: **в покое (`p` = 0 или 1) картинка должна быть идеальной**. В «Пикселях» без
проверки `step(0.001, p) · step(p, 0.999)` слайд в покое был бы разбит на 200 клеток.

### Кадры только во время перехода

Обычный эффект рисует 60 кадров в секунду постоянно. Слайдеру это не нужно: между переходами
картинка стоит. Поэтому для слайдов `running()` требует `slide.active` (идёт переход) или
включённую автопрокрутку. В покое — **ноль кадров**.

### Управление

```js
const slider = mount(document.querySelector('#slider'))   // все <img> внутри — слайды
slider.next()
slider.prev()
slider.goTo(2)
slider.index      // какой слайд показан (или к какому идёт переход)
```

Переход во время перехода: если новый клик пришёл, когда старый переход прошёл больше
половины, следующий начинается с того слайда, что уже почти виден, — без «прыжка» назад.

`duration` и `autoplay` рантайм читает из параметров эффекта сам.

### Без WebGL

Слайды — обычные `<img>`. Видна первая, остальные `hidden`. Без WebGL пользователь увидит
первый слайд, а поисковики — все картинки с их `alt`.
